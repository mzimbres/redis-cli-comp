# Redis client comparison

Redis most advertized selling point is performance. As an
_in-memory_ database it promises low-latency solutions for
typical backend needs: caching, queuing, rate limiting etc.

The Redis server however is only one side of the equation.
Clients on the other end must be capable of using the server
efficiently for the performance of the system as a whole to
be great.

In this article we profiled the performance of the most
popular client simulating the scenario where Redis is mostly
used, namely, on internet facing servers (mostly HTTP) that
serve connections concurrently while perhaps receiving some
form of pubsub events (server pushes).

The benchmark consists of

  1. starting multiple sessions that issue commands in a loop.

  2. subscribe to the channel to receive server pushes e.g.
     pubsub events.

Remarks

  - For the purpose of benchmarking _HTTP sessions_ are
    simulated as independent tasks in the benchmark app,
    goroutines in Go, coroutines in C++ etc.

  - Since the goal is to benchmark clients and not the
    server the lightweight PING command are used to simulate
    the interaction with the database.

  - The pushes in 2. are generated by sending PUBLISH
    commands in 1. in addition to the `PING`s.

## Parameters

The benchmark described above was implemented with the
following parameters (see the source files)

Parameter | counter | Description
----------|---------|------------
`SESSIONS`| 1000    | Number of sessions
`PINGS`   | 5       | Number of `PING` commands sent in each loop interation by each session
`REPEAT`  | 10000   | Number of loop interactions

The traffic generate by the parameters above reads

Type      | Count | Bytes
----------|-------|--------
Requests  | 60M   | 1.130Gb
Responses | 60M   |   390Mb
Pushes    | 10M   |   430Mb

That means, 1.130Gb are sent as requests and 820Mb are
received, either as response to the request or as a server
push.
