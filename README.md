# Redis client comparison

The most important Redis selling point is performance. As an
_in-memory_ database it promises a low-latency solution for
typical backend needs: caching, queuing, rate limiting etc.

The Redis server however is only one side of the equation.
It does not matter how fast its reaction times are if
clients on other end can't make proper use of that
performance and push it to its limits.

A large subset of Redis users are internet facing servers
(mostly HTTP) that serve connections concurrently while
perhaps receiving some form of pubsub events. Using this
observation we can benchmark Redis client libraries by
writing a apps that

  1. start multiple sessions that issue commands in a loop.

  2. Subscribe to the channel to receive server pushes e.g.
     pubsub events.

Remarks

  - Sessions above refer to coroutine (c++), goroutine (go),
    tasks (rust).

  - Since we are benchmarking clients the commands in 1.
    should be lightweight to the server, such as the `PING`
    command.

  - The pushes in 2. can be generated by issuing a PUBLISH
    command in 1. in addition to the `PING`s.

bug or misuse of the library, which is being clarified in
[this](https://github.com/aembke/fred.rs/issues/367) issue.

## Parameters

The benchmark elaborated above to implemented with the
following parameters (see the source files)

Parameter | counter | Description
----------|---------|------------
`SESSIONS`| 1000    | Number of sessions
`PINGS`   | 5       | Number of `PING` command in each loop interation by each session
`REPEAT`  | 10000   | Number of loop interactions

These number result in the following dataflow

Type      | Count | Bytes
----------|-------|--------
Requests  | 60M   | 1.130Gb
Responses | 60M   |   390Mb
Pushes    | 10M   |   430Mb

That means, 1.130Gb is sent as requests and 820Mb is
received, either as response to the request or as a server
push.

## Conclusion

The intrinsic performance difference of the languages used
to implement the clients cannot account for the performance
differece in the benchmarks.
